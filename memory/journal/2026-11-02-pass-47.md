## What changed

This is a teaching pass, not a feature pass. No command, table, adapter, port or
product behaviour changed. The work was to finish the written curriculum against
the code that exists, make the curriculum part of the memory gate, and correct
one quickstart that described a Docker path the code refuses to take.

### Fourteen lessons, one machine record

`memory/vault/05-Learning/` now has all 14 lesson files. Each one follows the
same shape: a real failure, the naive version, the actual source, one safe
change, and what the repository rejected. The exercises use files and package
scripts that exist now; the proof command in each lesson is the focused check
for the behaviour it teaches.

`memory/machine/lessons.json` is the new machine record. It lists each lesson's
order, path, source files, proof commands, and any count it teaches. The
Curriculum index stays the human table; the machine file is the contract behind
it.

`pnpm memory:check` now enforces that contract:

- every lesson in the Curriculum has a file, and every file is linked back;
- every `path` in `lessons.json` is its real file;
- every source `file` exists;
- every proof command starts with `pnpm`, names a real package script and a path
  that exists;
- the lesson contains its proof command and the five required sections;
- lesson order is 1..n with no gaps and no duplicate ids;
- a taught count must name a source (`limit`, `contextMenuLimit`, `migrations`,
  `modules`, `roots`, `subcommands`, `actions`, `contextMenus`, `liveChecks` or
  `lessons`) and must equal the value recomputed from `commands.json`,
  `live.json` or `project.json`.

That last rule is the point of the pass. A lesson may say "100 global roots" or
"13 live checks" because `commands.json` and `live.json` are the sources; change
either machine file and the lesson fails the gate until it is corrected. The
number is no longer a sentence the reader has to trust.

The lessons cover the last four passes directly:

- **Lesson 8** explains why the timer queue is bot-side and why expiry is a

### The Docker quickstart now matches the code

The README's "all-in-one Docker" step ran `docker compose up --build`, which
starts the optional `web` service with `NODE_ENV=production`. `apps/web/src/runtime.ts`
refuses that boot without a valid `SESSION_SECRET`. A gateway-only reader following
the old step would get a failed web container even though the bot and worker were
healthy.

The README now gives the honest split:

```bash
docker compose up --build bot worker   # gateway + worker, no dashboard
docker compose up --build              # also starts web; set SESSION_SECRET first
```

Lesson 14 teaches the same split and explains why the dashboard is optional.
This is a documentation correction, not a compose change: the production guard
is correct, and the quickstart was wrong to hide it.

## What we tried and rejected

- **A `pnpm lesson:verify` script.** Rejected: `pnpm memory:check` already runs
  inside `pnpm check`, and a second command would become a second gate with its
  own drift. The lesson metadata belongs with the memory validator.
- **Trust the lesson prose and review it by eye.** Rejected: a count in a
  sentence has no owner. The `facts` source is the owner; the gate follows it.
- **Put `probe:live` inside `pnpm check`.** Rejected again: CI has no Postgres,
  Redis or Docker, and the token-free gate must stay runnable on a laptop.
- **Make the Docker step always `bot worker`.** Rejected: the dashboard is real
  and some operators want it. The fix is to state the secret requirement and
  give both commands, not to hide a supported service.
- **One lesson per module.** Rejected: 12 module tours would teach file names,
  not decisions. The lessons follow the mechanisms a contributor must change —
  dispatch, guards, settings, cases, jobs, timers, evidence, live proof.
- **A Components V2 or sharding lesson.** Rejected: `packages/ui` does not exist
  and the bot does not shard. Writing either now would be a design essay with no
  runnable change.
