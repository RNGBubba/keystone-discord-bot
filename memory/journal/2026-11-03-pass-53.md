# Pass 53 — Dashboard analytics over the ledgers we already keep

**Date:** 2026-11-03
**Phase:** P6
**Carrier:** the framework-free `apps/web` app, unchanged. Analytics is a read
over the existing kernel port, not a reason to add a second server or a UI
framework.

## What changed

The P6 bullet says "analytics aggregates". The analytics module already owns the
read model, so this pass exposed that model through the dashboard instead of
building another one.

- `GET /dashboard/guilds/:id/analytics?days=N` renders a read-only page.
  `GET /api/v1/guilds/:id/analytics?days=N` returns the same
  `AnalyticsSnapshot` as JSON. Both call `DashboardService.analytics`, which
  delegates to the existing `AnalyticsStore.snapshot` behind
  `authorizeGuild`. There is no new query, table or writer.
- The window is bounded to 1–90 days, matching `/analytics`; the page offers
  7/30/90-day links. Invalid values are `400` before the store is called.
- The page prints every source table and its row count (`logging_events`,
  `cases`, `invite_joins`, `tickets`, `command_usage`), distinguishes current
  state (open tickets, active cases) from window counts, and always states that
  these are retained rows, not estimates.
- A window with no rows gets an explicit notice; it is not rendered as a
  confident zero. A web process without a shared database adapter (memory mode)
  says analytics is unavailable instead of showing zeros it cannot justify.
- Migration 0017 adds only the four missing read indexes the window queries
  need: `cases(guild_id, created_at)`, `invite_joins(guild_id, joined_at)`,
  `tickets(guild_id, created_at)` and a partial `tickets(guild_id, closed_at)`.
  `logging_events` and `command_usage` already had their guild/time index.
- The guild overview links to the analytics page.

## What we tried and rejected

- **A new dashboard aggregate query or `analytics` table.** Rejected: the
  existing `AnalyticsStore` is the one read model and the module's Status page
  already says to reuse it. A second query path could disagree with `/analytics`.
- **Adding AI usage/cost to this slice.** Rejected: the plan's bullet does not
  define an AI aggregate and the analytics spec deliberately stops at the five
  existing ledgers. Inventing a metric would be worse than leaving it out.
- **Showing a zero dashboard in memory mode.** Rejected: the standalone web
  runtime does not share the bot's in-memory stores, so zeros would be a claim
  the process cannot support. It names `DATABASE_URL` instead.
- **Leaving the window unbounded.** Rejected: 90 days is the command's cap and
  keeps the five queries bounded; the new indexes cover the remaining
  guild/time filters.
- **Creating a nightly rollup.** Rejected: it would duplicate rows and make the
  printed numbers unauditable. The source table counts are the reconciliation.

## Verification

- `pnpm typecheck` — pass.
- `pnpm test` — **533 tests in 80 files**, including service/render tests for
  bounded windows, refusal, the empty state and memory mode, HTTP tests for the
  page and API, and PGlite assertions that all four indexes exist.
- `pnpm probe:live` — **18/18**, adding `web-analytics-aggregates`: seeded seven
  audit rows, three cases, two invite joins, three tickets and three command
  runs in the real Postgres tables. The dashboard API and page matched every
  aggregate, including 120-minute average close and one SLA breach; an empty
  guild said it had no retained rows; `days=91`/`abc` were refused at `400` and
  signed-out reads at `401`. OAuth exchange used a fake port.
- `pnpm check` and `pnpm build` — run in the gate.

## Remaining phases, in the order that can still land

1. **P6 session hardening** — refresh/rotation, revocation on logout, per-route
   rate limits, `owners[]`. No external input needed.
2. **P6 API v1** — hashed scoped tokens, OpenAPI, idempotency, webhooks and
   per-token limits. No external input needed.
3. **P7 interactions and UI** — Components V2 and i18n; the MCP cannot click a
   button, right-click or invoke a slash command, so a human Discord client is
   required for the gateway half. The token-free adapter tests can land here.
4. **P8 playback** — needs a Lavalink node or a Discord voice client plus a
   Java 17 runtime; neither is available in this environment. The existing
   refused-playback path is the honest fallback.
5. **P9 launch and teaching** — docs, listings and the self-host guide can land;
   a real public launch and the live OAuth/login round trip need credentials and
   a human account.
6. **P10 scale** — sharding and load tests need a large guild set or synthetic
   load infrastructure; this environment cannot prove production p95.

**Live Discord OAuth** remains blocked without a real Discord client id/secret,
a registered redirect URI and a human browser login. Do not mark P6 complete
until that round trip, session hardening and API v1 are real.

## Next

Session hardening, then API v1. Keep analytics a read over `AnalyticsStore`; if
`command_usage` retention becomes a problem, prune it rather than adding a
rollup.
