# Pass 52 — Saved templates, the last template slice

**Date:** 2026-11-03
**Phase:** P6
**Carrier:** the existing framework-free `apps/web` HTML app. A Next.js shell
would add a second renderer and a second auth/session stack for no new proof;
nothing in this slice needs it.

## What changed

An admin can now save a guild's effective module settings as a named template,
list it, rename or refresh it, delete it, and apply it to selected guilds through
the same path the three built-in presets use.

- `packages/kernel/src/saved-templates.ts` defines `SavedTemplateStore` and the
  in-memory adapter: guild-scoped list/get/create/update/delete, one typed
  `SavedTemplateNameTakenError`, and a case-insensitive name rule. It is a
  snapshot store, not a settings store.
- Migration 0016 creates `config_templates` with a JSONB module snapshot and a
  unique index on `(guild_id, lower(name))`. `DrizzleSavedTemplateStore` maps a
  PostgreSQL `23505` back to the same typed error. Portability restore and
  deletion also clear a guild's templates, like every other guild-owned row.
- `DashboardService.createSavedTemplate` reads every module through
  `SettingsService.get`, strips credential-shaped keys with the existing filter,
  parses each snapshot with that module's own Zod schema, stores it, and appends
  one `template.create` audit row with actor and `source: dashboard`.
- `updateSavedTemplate` edits name/description and can refresh the snapshot from
  the guild's live settings through the same schema gate. Every accepted edit
  moves `updatedAt` forward by at least one millisecond, so a preview taken
  before it is always stale. `deleteSavedTemplate` removes the row and appends
  `template.delete`; the audit rows survive.
- `previewSavedTemplate` validates the stored modules against the current
  registry and schemas. An invalid row returns a plan with template-level issues
  and no targets, so the page reports each bad path and apply stays disabled.
  A valid row is diffed per guild with the existing `diffSettings`; the
  fingerprint seed includes the template id and `updatedAt`.
- `applySavedTemplate` refuses an invalid row at `400`, a mismatched fingerprint
  at `409`, then calls the shared `applyPlan`; that loop is the single write path
  for built-in and saved templates and calls `SettingsService.update` per changed
  module. Each accepted write appends one dashboard audit row.
- Routes: `GET|POST /dashboard/guilds/:id/templates`, `GET|POST
  /dashboard/guilds/:id/templates/:templateId`, `POST .../delete`,
  `POST .../preview`, `POST .../apply`. Every write goes through
  `requireSettingsWrite` (session → guild authorization → CSRF) and the
  multi-guild selection through `authorizeFleet`.
- Pages: a list with a save form, an editor with metadata, refresh, a target
  picker, the audit trail and delete. The shared template preview page now takes
  an apply action/back link and renders template-level schema issues.

## What we tried and rejected

- **A separate saved-template service.** Rejected: it would duplicate the plan,
  fingerprint, re-authorization and audit loop. `applyPlan` is now shared by the
  built-in and saved paths instead.
- **A second settings schema or per-field template editor.** Rejected: a
  template is a snapshot of effective settings. Editing individual fields would
  be a second settings editor and a second place for schema drift.
- **Storing the source guild's raw settings rows.** Rejected: the snapshot is
  the parsed effective value per module, so defaults and future schema additions
  behave exactly as they do on the source guild. Credential-shaped keys are
  omitted rather than stored.
- **Applying an invalid stored row best-effort.** Rejected: a row edited outside
  the dashboard (or saved before a schema change) reports every issue and writes
  nothing. This is the difference between a repair tool and silent corruption.
- **A marketplace across guilds.** Out of scope: a saved template belongs to the
  guild that saved it. Cross-guild apply still requires the actor to manage both
  guilds and still previews each target.
- **A Next.js migration in this pass.** Rejected: the slice needed routes,
  widgets and proof, not a new framework. The carrier question is answered below,
  not assumed.

## Verification

- `pnpm typecheck` — pass.
- `pnpm test` — **526 tests in 79 files**, including new kernel store tests, a
  PGlite adapter test and service/HTTP tests for save, list, edit, refresh,
  tampered/stale refusal, invalid-stored-row refusal, audited create/update/delete
  and one audited write per guild.
- `pnpm probe:live` — **17/17**, adding `web-saved-templates` over the real local
  HTTP server and Postgres. The probe saved a template from one guild, listed it,
  previewed a two-guild diff without writing, refused a tampered fingerprint and
  an edited template's old preview at `409`, applied one write per guild with one
  `source: dashboard` audit row each, edited a stored row out of schema validity,
  saw the page/preview report it and the apply refuse at `400`, and confirmed
  audited delete. The OAuth exchange used a fake port.
- `pnpm check` and `pnpm build` — run in the gate; memory regenerated from machine
  truth.

## Remaining P6, in the vault's order

1. **Analytics aggregates** — one read-only aggregate view/API over the existing
   tables; no new writer. Size: one small pass.
2. **Session hardening** — refresh/rotation, Discord revocation on logout,
   per-route rate limits and `owners[]`. Size: one to two passes.
3. **Public API v1** — hashed scoped tokens, OpenAPI, `Idempotency-Key`,
   webhooks and per-token limits. Size: two to three passes.
4. **Live Discord OAuth** — the code path exists and is tested with a fake port;
   the round trip needs real Discord client credentials, a registered redirect
   and a human login. Size: one short pass, blocked in this environment without
   credentials.
