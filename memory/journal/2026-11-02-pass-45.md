## What changed

This is the first P7 completion slice with a real scheduler. It covers the two
features that share one mechanism: a temporary moderation action that must be
released later, and a reminder or scheduled message that must be delivered
later. Panic mode and goodbye messages are event-driven and command-driven
respectively; they are not part of this timer slice and stay open.

### One timer mechanism, consumed where Discord is available

The worker from pass 44 owns database jobs but has no Discord client. Sending a
scheduled message or lifting a ban from the worker would require a second
Discord adapter (REST) beside the gateway adapter, and two adapters can diverge
on permissions, channel resolution and error handling. That is the wrong trade
for this codebase.

Instead the bot creates a delayed queue on the same BullMQ driver, named
`<QUEUE_NAME>.bot`, and is its only consumer. In memory mode the same code uses
`InProcessJobQueue`. The module services are the same services commands use:

- `moderation.expire` calls `TemporaryActionService.expire(caseId)`.
- `content.deliver` calls `ContentService.deliver(guildId, kind, id)`.

The worker queue is unchanged. The split is by capability, not by feature:
database-only work goes to the worker; a job that must touch a guild goes to the
bot process.

### Temporary bans and temporary roles

- Migration `0014_case_expiry` adds nullable `cases.expires_at`, indexed only
  for rows that have it.
- `/mod ban` accepts an optional `duration` in minutes. `/mod temp-role` is a
  new subcommand with `user`, `role`, `reason`, `duration` and `dry_run`; it
  adds the role, records `{ roleId }` as evidence and schedules its removal.
  A subcommand costs no global command root.
- The case is written before the Discord action, as every other `/mod` action
  already was. `expiresAt` is written only after the action succeeds.
- Scheduling  enqueues one job with `idempotencyKey =
  moderation:expire:<caseId>` and a delay to the due time. The key has exactly
  three colon-separated parts because BullMQ 6 permits a colon in a custom id
  only for that legacy shape; the in-process test asserts the shape so this
  cannot regress. If the enqueue
  itself fails, the case still carries `expiresAt`; startup recovery will
  reschedule it.
- `CaseStore.claimExpiry` clears `expires_at` with `UPDATE … WHERE expires_at IS
  NOT NULL AND state NOT IN ('closed','reversed') RETURNING *`. Only the worker
  that wins that update performs the release. On failure the timestamp is
  restored and a `note` event records the external error, so the case remains
  retryable instead of being silently closed.
- Success appends an `expired` event and closes the case. `caseEmbed` shows the
  release time when present.
- At `ClientReady`, each guild runs `TemporaryActionService.recover`: overdue
  cases expire now, future cases are re-enqueued. That is the memory-mode
  restart path; BullMQ already keeps the delayed job in Redis.

### Reminders and scheduled messages

- `/tools reminder` and `/tools schedule` still write the same
  `community_records` rows. They now also enqueue `content.deliver` with a due
  delay and an idempotency key.
- `ContentService.deliver` re-reads the record, refuses a future due time, and
  claims it with `claimSent` before sending. That claim is one conditional
  `UPDATE … WHERE data->>'sent' <> 'true' RETURNING *`; only its winner sends,
  and a failed send puts `sent:false` back so a retry can try again. A
  redelivered timer is therefore a no-op.
- `tick()` calls the same `deliver` method, so the existing message/
  reconciliation path and the timer path cannot drift. The claim is what makes
  running both safe: a read-then-write check would let the timer and the sweep
  both see `sent:false` and send the same reminder twice.
- The old 60-second tick remains for feed polling, giveaways, delayed autoroles,
  birthdays, seasons and stat channels. It is no longer the only delivery path
  for reminders/schedules; it is a reconciliation backstop.

## What we tried and rejected

- **Run expiry in the worker with a Discord REST adapter.** Rejected: it would
  create a second Discord adapter with a second permission/error model. The
  worker's value is database work, not pretending to be the gateway.
- **Use the existing 60-second interval as the only scheduler.** Rejected for
  delivery: a minute of drift is visible for reminders, and a process restart
  before the tick loses the in-memory wake-up. Keeping it as a backstop is
  different from making it the promise.
- **Use a separate `scheduled_jobs` table and poll it from the bot.** Rejected:
  it is a second scheduler beside BullMQ, with its own retry and leasing rules.
  The case/record row already holds the durable due time.
- **Close the case before calling Discord.** Rejected: a Discord failure would
  leave a closed case while the ban or role is still in force. Clearing the
  timestamp as a claim and restoring it on failure keeps the action and the
  record aligned.
- **Put the role id only in the action's `reason` string.** Rejected: the expiry
  handler would have to parse prose. The role id is explicit evidence on the
  case.
- **Trust `if (!record.data.sent)` as the only guard.** Rejected during review:
  the timer and the 60-second sweep can both read `sent:false` before either
  writes, which sends the reminder twice. The store now owns an atomic claim.
- **Mark every row `liveVerified: true` because the probe passed.** Rejected.
  The live probe proves the SQL, queue and service path with a recording
  Discord port. It does not send to a guild. The three timer rows stay
  `liveVerified: false` and their notes name the check and the boundary.
