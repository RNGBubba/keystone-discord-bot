# Pass 61 — P7: every community component id is signed and routed

**Date:** 2026-11-03
**Phase:** P7
**Carrier:** the existing `ComponentSigner`/`ComponentRouter`, `modules/community`
services and `apps/bot/src/components.ts`. No new package, table, command or
listener.

## What changed

- **The five families are signed at the source.** `ReactionRoleService`,
  `GiveawayService`, `SuggestionService` and `ContentService` now take the
  bot's `PanelSigner` and mint `k1:` ids through it, so the panel poster and
  the router verifier share one secret. Posting a panel without a signer is a
  `UserError` before any message is sent; an unsigned control is impossible by
  construction.
- **Namespaces and payloads.** `role:toggle` carries the role id,
  `roles:select` the panel id, `giveaway:enter` the giveaway id,
  `suggest:up`/`suggest:down` the suggestion id, and `poll:v0` … `poll:v4` the
  poll id with the option index in the action. The payload stays a plain
  record id and stays under the signed 40-character budget.
- **TTLs are deliberate.** Role panels are pinned configuration, so they get a
  year (`ROLE_PANEL_TTL_MS`); giveaways, suggestions and polls get 30 days
  (`COMMUNITY_PANEL_TTL_MS`). The ticket panel keeps its existing 30 days.
- **One router, five routes.** `apps/bot/src/components.ts` registers the role
  button, the select menu, giveaway entry, both suggestion votes and one poll
  route per option. Each handler calls the same service as the old listener:
  `toggle`/`applySelection`, `enter`, `vote`. No threshold, balance or
  permission rule moved into the adapter.
- **The legacy listener is gone.** The whole `InteractionCreate` block and its
  `ReactionRoleService`/`SuggestionService` imports were deleted from
  `community-events.ts`. `registerCommunityEvents` still receives the signer,
  but only so the minute tick can render a signed, disabled button when it ends
  a due giveaway.
- **Tests.** The community tests parse the posted ids, the router tests press
  each of the five through real stores, and `community-events.test.ts` proves a
  legacy community id gets no reply. The probe adds
  `web-community-interactions`.

## The inventory

After the migration, this is the complete search for component ids outside the
router:

```text
rg -n 'customId|keystone:' -g '*.ts' modules apps
```

Every `modules/community` id is now minted by `PanelSigner`; no literal
`keystone:` remains in that module. `apps/bot/src/community-events.ts` has no
component handler. The one remaining bypass is moderation:

```text
apps/bot/src/components.ts:  isModerationButton() → handleModerationButton()
apps/bot/src/moderation-buttons.ts: APPEAL_PREFIX = "keystone:appeal:"
                                    VERIFY_PREFIX = "keystone:verify:"
```

`keystone:appeal:` and `keystone:verify:` still go to their own handler. The
appeal id could move to `native` `appeal:open` with a case-id payload today.
The verify id cannot without a redesign: it must carry both the guild and the
member so a DM button knows where to verify, and a full Discord snowflake pair
(`19 + 1 + 19`) is 39 characters before the signed prefix — over the
`ComponentSigner`'s 40-character payload budget once the action is encoded.
Shrinking the pair to base36 is possible but is a payload design decision, not
a routing cleanup, so this pass scopes the claim: **all community, ticket and
form component ids are signed and permission-checked; moderation's two ids are
not, and are named here.**

## What we tried and rejected

- **Passing a signer through every service constructor position.** Rejected:
  `GiveawayService` already has `now` and `rng`, and a public options object
  would have changed every call site for no reader benefit. The signer is the
  last optional argument and only the panel-creating methods require it.
- **Signing in the command layer and passing ids into the services.** Rejected:
  `start`, `submit` and `createPoll` generate their record ids internally, so
  the command would have to know a record before it exists or the service would
  have to accept an id it cannot trust.
- **One `poll:vote` route with `pollId:index` in the payload.** Rejected: the
  index plus a UUID is 38 characters and forces delimiter parsing; the action
  already carries the index just as safely and keeps the payload a plain id.
- **A one-month TTL for the role panel.** Rejected: a pinned self-assign panel
  silently dying after a month is a product regression, not a security gain.
  The id still expires; the window matches the surface's lifetime.
- **Keeping a disabled `keystone:` button on an ended giveaway.** Rejected: it
  would keep a legacy id in every ended panel and defeat the inventory. The
  ended button is signed and disabled when a signer is available, and omitted
  otherwise.
- **Extending the signed payload budget to fit moderation's verify id.**
  Rejected for this pass: it changes the kernel's id format for two routes and
  needs a migration story for every panel already posted. The honest scope is
  better than silently enlarging a shared contract.
- **Moving the community replies into the i18n catalog at the same time.**
  Rejected for scope: the replies are byte-identical to the old listener, and
  translating them is the next named slice.
