# Pass 56 — P6 signed webhooks and `Idempotency-Key` replay

**Date:** 2026-11-03
**Phase:** P6
**Carrier:** the framework-free `apps/web` app. The outbox, the signing key and
the drainer live where the dashboard already is, not in `apps/worker`: that
process has no web dependencies and no reason to hold the sealing key. The rows
are durable, so a future worker can drain the same table without changing the
port.

## What changed

- **One webhook port, two adapters.** `packages/kernel/src/webhooks.ts` declares
  `WebhookStore` (subscriptions, enqueue, due, complete, fail, receipts), the
  three subscribable events (`settings.updated`, `api_token.issued`,
  `api_token.revoked`), the retry constants and an in-memory adapter. Migration
  0019 creates `webhook_subscriptions` and `webhook_deliveries`, with the due
  index the drainer's only query needs; `DrizzleWebhookStore` is the Postgres
  adapter and deleting a subscription cascades its receipts.
- **The signing secret is shown once.** `WebhookService.create` mints
  `whsec_…`, seals it with the same `SecretBox` the session and Discord tokens
  use, and returns the plaintext only to the creation response. The stored row is
  the sealed value; the probe checks that the plaintext is not in the table.
- **Delivery is an outbox row, not a fire-and-forget call.** A row is written
  before the network is touched with `status=pending`, `attempts=0` and
  `next_attempt_at=now`. The drainer attempts due rows, signs each body with
  `t=<unix>,v1=HMAC-SHA256(<t>.<body>)`, and writes back one of two facts:
  `delivered` with the HTTP status, or a retry at
  `now + 250ms * 2^(attempt-1)`. The third failure is terminal and keeps the
  last error and status.
- **One drainer in the web runtime.** `startWebhookDrainer` is started by
  `apps/web`'s runtime and stopped with it; the interval is unref'd, a slow
  drain cannot overlap itself, and a failure is logged without killing the
  process. The probe runs the same drainer, so retry timing is the shipped one.
- **Events come from the write paths that already exist.**
  `DashboardService.update` enqueues `settings.updated` with the module, actor
  and source after the settings write succeeds; token issue and revoke enqueue
  their own events. No second writer and no polling of the settings table.
- **Administration is the normal gate.** `GET/POST /dashboard/guilds/:id/webhooks`,
  `POST …/:webhookId/test` and `POST …/:webhookId/delete` use session → guild
  authorization → CSRF and append `webhook.create`, `webhook.test` and
  `webhook.delete` rows with `source: "dashboard"`. A URL must be `https:`, or
  `http:` only on loopback so a local receiver can be tested; credentials in the
  URL are refused; the events are checked against the kernel list and default to
  all of them.
- **`Idempotency-Key` reuses the receipt table.** `apps/web/src/idempotency.ts`
  namespaces the key by principal (`http:<actor>:<key>`), and
  `requestFingerprint` hashes `METHOD path\nbody`. `routes/api.ts` claims the
  receipt before the write, replays the stored status and bytes with
  `Idempotent-Replayed: true`, refuses a different body at `409
  idempotency_conflict`, and releases the claim when the write throws so a
  corrected retry is not stuck behind the lease. The first call is the only one
  that writes settings or an audit row.
- **A replay is byte-identical.** `job_receipts.response_body` is `text`, not
  `jsonb`: jsonb normalises key order, so the second response would not be the
  first response. The adapter stores `JSON.stringify(body)` and parses it on
  replay; `packages/db/src/idempotency.test.ts` asserts the exact bytes.
- **UI.** The guild page lists each endpoint with its events, shows the one-time
  secret after creation, and prints the newest ten delivery receipts with status,
  attempts, last HTTP status and the last error. The fleet/overview page links to
  it.
- Tests: 8 webhook service tests (URL rules, sealed secret, signing/verification
  and a stale timestamp, retry then terminal failure, event fan-out, receipt
  ordering), 3 PGlite store tests (round trip and guild scoping, due/complete/
  retry, cascade), 2 PGlite idempotency tests (replay and exact bytes, release
  and lease), and 5 HTTP tests (create/list/delete behind the gate and audited,
  test ping delivered, body mismatch, anonymous/wrong-scope refusals, invalid
  input).

## What we tried and rejected

- **A webhook-specific delivery table or a second replay mechanism.** Rejected:
  `job_receipts` already answers "has this key been seen, and what did it
  answer", and the queue uses the same claim rule. Two mechanisms would drift.
- **Sending deliveries through BullMQ.** Rejected for this slice: the worker has
  no sealing key, and handing it one would spread the dashboard's secret across
  processes. The outbox plus one drainer is the smaller correct step; the store
  contract does not change if the drainer moves later.
- **Fire-and-forget `fetch` after the response.** Rejected: a restart would lose
  the event, and the admin would have no receipt to read. The row is the
  promise.
- **A subscription-supplied signing secret.** Rejected: an operator would reuse
  a password, and the "shown once" rule would be a suggestion. The server mints
  it and stores only the sealed value.
- **`jsonb` for the replayed response.** Rejected after the first live run: the
  probe compared the two bodies and Postgres had reordered the keys. Storing the
  exact JSON text is the only way `Idempotent-Replayed` can mean "the same
  response".
- **Retrying forever or failing on the first 500.** Rejected: a receiver that is
  briefly down is normal; a receiver that is gone forever must not accumulate
  rows. Three attempts with backoff, then a visible terminal receipt.
- **Trusting the probe's own signature helper.** Rejected: the probe recomputes
  the HMAC with `node:crypto` from the delivered body and headers, so a bug in
  `verifyWebhookSignature` cannot certify itself.
- **Letting a failed earlier probe run poison the next.** Fixed: the web block
  now starts from a clean state for its two guilds, so the audit-count checks
  measure this run rather than the last one.

## Verification

- `pnpm typecheck` — pass.
- `pnpm test` — **569 tests in 85 files**.
- `pnpm probe:live` — **22/22**, adding two checks over real local HTTP on
  Postgres:
  - `web-webhooks`: created an endpoint behind the guild write gate; the
    `whsec_` secret was shown once and the column held only the sealed value; a
    test ping reached a local receiver and its `t/v1` signature verified with an
    independent HMAC; a `settings.updated` event arrived with the module, actor
    and source; an always-500 receiver was attempted three times, then the page
    showed a `failed` receipt with HTTP 500; both removals left dashboard audit
    rows; a non-loopback `http:` URL was refused at `400`.
  - `web-idempotency-key`: the same `settings:write` token sent the same key and
    body twice; the second response said `Idempotent-Replayed: true` and was
    byte-identical, the same key with a different body was `409
    idempotency_conflict`, exactly one `settings.update` audit row existed, and
    the receipt stored the fingerprint and the 200 response.
- `pnpm check`, `pnpm build`, `pnpm memory:check` — run before the PR.
