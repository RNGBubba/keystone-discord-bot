# Pass 49 — P6 schema-driven settings widgets and an audited settings write

## What changed

**The dashboard carrier stays `apps/web`.** The approved plan allowed either a
Next.js shell or the existing framework-free HTML app. This pass extends the
existing server-rendered app: its authorization, CSRF, session and `SettingsService`
seams are already proven, and a client framework would add a build pipeline and a
bundle without adding a capability. There is still no `packages/ui`, no React and
no second settings store.

**The settings editor is generated from the module's Zod schema.** A new
`apps/web/src/settings-form.ts` walks the schema and produces one form model:
booleans become checkboxes, bounded numbers become number inputs with the real
min/max/step, enums become selects, short strings become text inputs, long
strings become textareas, primitive arrays become one-per-line boxes, and
records / arrays of objects fall back to a JSON box that the same schema still
validates. The form posts named fields plus a `__rendered` marker, so an
unchecked box means false while a field the form did not render is untouched.
The parser turns those fields back into a nested patch; the route passes that
patch to `DashboardService.update` → `SettingsService.update`, which parses
against the owning module's schema. Field-level Zod issues re-render the same
page at `400` with the submitted value preserved; nothing is stored.

**Settings writes and resets now append an audit row.** `packages/kernel/src/audit.ts`
adds the `AuditStore` port, an in-memory adapter and `diffSettings`, which
flattens changed leaves to dotted paths. `SettingsService.update` and `reset`
append to `audit_events` when a store is wired: actor, action, module and the
dotted-path before/after diff. A no-op or a rejected write appends nothing.
`packages/db/src/audit-store.ts` is the SQL adapter. The bot and web composition
roots wire it; `/config set`, `/setup module` and `/setup reset` pass the
command actor, and the dashboard/API pass the signed-in user with
`source: "dashboard"` or `"api"`. The settings page shows the newest audit rows
for that module, so the proof is visible in the product, not only in a table.

**Two defects surfaced and were fixed.** The old secret-key filter matched
`maxOutputTokens` because it looked for `token` anywhere, hiding a real AI
setting from the dashboard; it now matches credential-shaped suffixes only. And
clearing an optional text widget used to leave an explicit `undefined` that a
JSON column could turn into SQL NULL, which the same optional schema rejects on
the next read; `SettingsService` now strips undefined values before persisting.

## What we tried and rejected

- **Adding a Next.js shell now.** It is still a reasonable later carrier, but it
  would replace proven security code with a client bundle before this slice
  proved a single schema-generated field. The existing HTML app also keeps the
  dashboard optional for gateway-only self-hosts.
- **A widget class for every Zod type.** The installed schemas use booleans,
  numbers, enums, strings, primitive arrays, records and refined strings. A
  small widget set plus a schema-validated JSON fallback covers every setting
  today and cannot silently drop a future shape.
- **A second web-only settings schema or whitelist.** The form model is a
  projection of the module's schema, and the write path still calls
  `SettingsService.update`; a second validator would drift from the bot.
- **Keeping the JSON textarea as the only editor.** It was honest but not a
  dashboard an operator could use, and it left `maxOutputTokens` hidden by the
  over-broad secret filter.
- **Auditing inside the settings transaction.** `SettingsRepository` and
  `AuditStore` are separate ports, and the SQL settings write already uses its
  own transaction. The audit row is appended immediately after the successful
  write; a future single-transaction port can remove the small gap. The current
  tests prove no audit row on rejection and one row on success.
- **Auditing a no-op.** Saving the same value writes the settings record but no
  audit row, because there is no change to report.
- **A web-only audit table.** `audit_events` already existed in the schema, the
  importer and the portability bundle. Reusing it avoids a second ledger.
- **A real Discord OAuth login for this proof.** The probe has no Discord user
  or browser. It uses a fake OAuth port for the code exchange, then drives the
  real login route, sealed state cookie, session store, CSRF gate, HTML form,
  `SettingsService` and Postgres audit table over local HTTP. Live Discord OAuth
  remains open and is not claimed.

- Focused tests green (43): the widget model/parser, the web login/write/audit
  flow, the kernel audit diff and reset, `/config` actor attribution, and the
  PGlite audit store.
- Full `pnpm check` green: typecheck, **488 tests / 73 files**, budget
  **20/100 roots · 141 subcommands · 161 actions · 4 menus**, claims 35/35,
  intents, channels and memory.
- `pnpm build` green for bot, worker, web, migrate and portability.
- `pnpm probe:live` **14/14** on Postgres 16.15 + Redis. The new
  `web-schema-widgets` check loaded the AI form over real local HTTP, saved
  `monthlyBudgetUsd=9` through the schema, saw one `audit_events` row naming the
  dashboard actor and source, then posted `5000`, got `400` with the field and
  value preserved, saw the stored value unchanged and saw no second audit row.
  The OAuth exchange itself used a fake port; no Discord login is claimed.
- `memory/machine/live.json` now records `live-2026-11-03` and 14 checks.
