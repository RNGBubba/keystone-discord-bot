# Pass 46 — Panic mode and goodbye messages

**Date:** 2026-11-02
**Phase:** P7
**Tree before:** `main` after pass 45 · 20 roots / 139 subcommands / 159 actions / 4 menus / 12 modules / 457 tests / 68 files

## What changed

This pass closes the two lifecycle features pass 45 deliberately left open: panic
mode and goodbye messages. Neither needs a scheduler, so the timer queue from
pass 45 is unchanged. The work is one command branch, one command subcommand,
one durable snapshot and one event handler.

### Panic mode is a persisted snapshot

`/mod panic state:status|on|off` lives under the existing `/mod` root. `status`
is readable by any caller with `ModerateMembers`; `on` and `off` also require
`Administrator`, because denying `SendMessages` in every text channel is a
server-wide action rather than a moderation action against one member.

The Discord adapter gained two port methods:

- `lockdown(guildId, reason)` iterates the guild's text-like channels
  (`GuildText`, `GuildAnnouncement`, `GuildForum`, `GuildMedia`), reads the
  `@everyone` SendMessages overwrite, records whether one existed and whether it
  was `allow`, `deny` or `neutral`, then writes `SendMessages: false`. A channel
  already denied is **not** in the snapshot, because restoring panic later must
  not unlock a channel an administrator locked on purpose.
- `restoreLockdown(guildId, locks, reason)` restores exactly that snapshot:
  delete an overwrite that did not exist, write `allow`/`deny`/`neutral` back
  when it did, and return the ids that succeeded and failed.

`PanicService` is the policy layer. It refuses a second `on` while active,
persists the snapshot **before** the command replies, and clears the row only
when every channel restored. If some restores fail it keeps only those channel
ids, so a second `off` retries the failures instead of touching restored
channels again. A start where no channel could be locked writes nothing.

The snapshot lives in one `community_records` row (`kind = moderation_panic`,
`key = state`) rather than a new table. It is one small JSON document per guild,
read by the panic command and written only while panic is active; a dedicated
table would add a migration and a second schema without a query benefit.
`packages/db/src/panic-store.ts` is a thin adapter over the typed-record seam,
so the SQL and in-memory implementations agree on the `PanicStore` interface.

There is no automatic expiry. A timer would add a second recovery path for the
snapshot without making the switch more reliable; the manual `off` is the
promise, and a future time-bounded lockdown should ride the pass-45 timer with
this snapshot rather than invent a second mechanism.

### Goodbye is welcome with the role and DM branches removed

`/tools goodbye` writes `goodbye.*` in the existing community settings:
`enabled`, `channelId` and `message`, with the same 1,500-character cap as
welcome. `WelcomeService.handleLeave` substitutes `{user}` and `{server}` and
sends one channel message. It deliberately has no autorole and no DM branch: the
member is already gone, a DM is not guaranteed, and a role grant would race
Discord's own member removal.

`apps/bot/src/community-events.ts` now subscribes to `GuildMemberRemove` beside
`GuildMemberAdd` and delegates to the same service. The adapter contains no
threshold or template logic, so the event test can emit a real discord.js event
and assert the configured text without a gateway.

### What this pass did not build

- Panic does not expire automatically, does not touch voice channels or
  thread-level overrides, and does not preserve allow/deny for permissions other
  than `@everyone` SendMessages.
- Goodbye is text-only. A Components V2 welcome/goodbye panel still has no
  `packages/ui` and is not claimed.
- No live gateway call was made: the MCP account is a bot, cannot be a target of
  these overwrites as a human admin, and cannot make a member leave. The
  Discord half is adapter-tested, not observed.

## What we tried and rejected

- **A dedicated `panic_snapshots` table.** Rejected for this slice: one row per
  guild with no query pattern beyond get/save/clear is exactly the typed-record
  seam. If panic later needs an audit history or a cross-guild query, a table is
  the right next step, not the first one.
- **Restore every channel to `allow`.** Rejected: that silently unlocks channels
  that were neutral or already denied before panic. The snapshot has to record
  what existed, and the adapter has to delete an overwrite that did not.
- **Snapshot only after the command replies.** Rejected: a restart between the
  Discord write and the reply would leave the server locked with no way back.
  The row is written first; the reply describes what was already durable.
- **Clear the row even when some restores fail.** Rejected: that loses the only
  record of which channels are still locked. Keeping the failures is what makes
  `off` a retry.
- **Give goodbye its own service and settings object.** Rejected: it is the same
  placeholders and the same settings port. A second service would duplicate the
  substitution and drift on the cap.
- **DM the departing member or grant/remove a role on leave.** Rejected: a
  leaving member may already be unreachable, and a role mutation races the
  gateway's member removal. Goodbye is a channel announcement, nothing more.
- **Assert the panic snapshot with `JSON.stringify` equality in the probe.**
  Rejected after the first live run: Postgres `jsonb` reorders object keys, so
  the probe failed even though the data was intact. The probe now compares the
  fields that matter. That was a test defect, not a product defect.
