# Pass 54 — P6 session hardening

**Date:** 2026-11-03
**Phase:** P6
**Carrier:** the framework-free `apps/web` app, unchanged. Hardening is four
changes on the existing opaque-session and authorization code, not a new auth
service.

## What changed

- **Session rotation.** `AuthService.resolve` re-keys an opaque session after
  `rotationIntervalMs` (15 minutes in the runtime) on a `GET`/`HEAD`. It mints a
  new random cookie and CSRF token, keeps the sealed Discord token and the
  absolute `expiresAt`, and calls the new `SessionStore.rotate` so the old id
  vanishes in one step. `request-context` appends the replacement cookies before
  the route runs, and `send` now appends `Set-Cookie` instead of overwriting a
  rotation a redirect would otherwise drop. `createdAt` is the issue time of the
  current credential; no migration was needed.
- **One-use replay.** A replayed pre-rotation cookie finds no row and gets `401`.
  Rotation is only attempted on safe methods: a `POST` carries a CSRF token
  minted for the old cookie, and rotating before the check would turn a valid
  form into a `403`.
- **Discord token revocation on logout.** `DiscordOAuth.revokeToken` is the new
  port method; the real adapter posts to `/oauth2/token/revoke`. `logout` revokes
  first, then deletes the local session, and deletes it even when Discord is
  unavailable. The route logs only that revocation was not confirmed, never the
  token.
- **Per-route limits.** `apps/web/src/rate-limit.ts` is a fixed-window limiter
  keyed by signed-in user or socket address, in four classes: `auth` (20 / 5
  min), `dashboard` (120 / min), `write` (30 / min) and `api` (60 / min).
  `server` applies it after session resolution and before dispatch, returns `429`
  with `Retry-After`, and exempts `/healthz`. The limiter is in-process because
  the dashboard is one self-hosted process.
- **`owners[]`.** `WEB_OWNER_IDS` (comma-separated Discord ids, validated) is the
  only instance-wide allow-list. `GET /dashboard/instance` shows deployment mode,
  session lifetime/rotation, owners and the rate budgets. The owner-only
  `POST /dashboard/instance/sessions/revoke` deletes every session row for a
  supplied Discord id through `SessionStore.deleteForUser`; it is not a settings
  write, so it appends no audit row, and it re-keys nothing. A guild
  Administrator or Manage Server is refused at `403`; anonymous is `401`.
- Tests: six new HTTP tests (rotation and replay, revocation before deletion,
  revocation failure still deleting, per-class `429` + recovery, anonymous limits
  plus `/healthz` exemption, owner/admin/anonymous gate and the revoke action)
  and one PGlite test for atomic re-key and per-user deletion.

## What we tried and rejected

- **Storing a Discord refresh token to implement "refresh".** Rejected: the
  contract says not to store a credential until refresh and single-flight exist.
  This pass rotates the opaque session cookie; it does not extend the Discord
  grant. Live revocation is the remote half, and it is asserted at the port only.
- **Rotating on every request including POST.** Rejected: it would invalidate the
  CSRF token the submitted form carries. Rotation is a safe-method action.
- **Adding a `rotated_at` column or migration.** Rejected: `createdAt` is already
  the issue time and `expiresAt` is the absolute end. Renaming the meaning in the
  comment is honest; a column no query needs is the drift pass 20 removed.
- **A shared Redis rate limiter.** Rejected for this slice: the web process is a
  single container and there is no second writer. An in-process fixed window is
  the accurate implementation; a multi-process deployment would need a shared
  counter, and that belongs with the API-token work, not a silent second store.
- **Per-URL limits.** Rejected: a new route would ship unlimited by default. The
  class budgets make every `/dashboard` page inherit the dashboard budget.
- **Letting a guild admin reach the instance console.** Rejected explicitly by
  the security contract: managing one server is not operating the deployment.
- **Revoking only remotely or deleting only locally.** Rejected: the browser
  session must die even if Discord is down, and the remote grant should not
  outlive a deliberate sign-out. Both happen, in that order.
- **A second server just to test limits.** The probe uses a second handler on the
  same auth/session/dashboard objects with tight policies and a movable clock, so
  the 429 proof does not throttle the long script or sleep through a real window.

## Verification

- `pnpm typecheck` — pass.
- `pnpm test` — **540 tests in 80 files**, including the new HTTP and PGlite
  cases.
- `pnpm probe:live` — **19/19**, adding `web-session-hardening`: the instance
  console was `401` anonymous, `403` for a guild admin and `200` for an owner;
  the owner's revocation deleted the admin's Postgres session and the cookie then
  failed; the auth, dashboard, write and API classes each returned `429` with
  `Retry-After` and recovered in the next window while `/healthz` stayed exempt;
  past the rotation interval the old cookie was refused and the new one worked;
  logout revoked through the OAuth port and the session then failed. The probe's
  OAuth exchange is fake, so live Discord revocation and login are **not
  claimed**.
- `pnpm check`, `pnpm build` — run in the gate.
