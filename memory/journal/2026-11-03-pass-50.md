# Pass 50 — P6 fleet view and previewed config templates

## What changed

**The dashboard has a fleet view.** `GET /dashboard/fleet` lists the guilds the
signed-in user can manage, with each guild's enabled modules. It reads settings
through `SettingsService` for every registered module; a stored row that no
longer parses marks that module unreadable instead of taking the page down. The
same two-check rule still guards every action: the fleet page uses the OAuth
manageable list, and preview/apply call `GuildAccessService.authorizeMany`,
which checks the selected guild against that list **and** checks bot membership
for each one before any settings are read or written.

**Three built-in templates, previewed before anything is applied.**
`apps/web/src/templates.ts` owns a template as a partial patch per module, not a
second settings store:

- alert-first moderation: every filter in `alert`, dry-run stays on;
- strict moderation: links/profanity/zalgo `delete`, invites `timeout`, mention
  cap five, dry-run off;
- quiet optional modules: AI and music disabled.

The preview deep-merges each patch over the guild's current settings, parses the
result with that module's own Zod schema, and diffs it with `diffSettings` — the
same helper the audit row uses. Records merge recursively, so a template can
change `automod.links` without wiping an operator's `bannedWords`; arrays replace
as one value. Nothing is written during preview.

**Apply is bound to the preview.** The preview page carries a SHA-256 fingerprint
over the template id, every guild's target and every before/after leaf. Apply
recomputes the plan from current settings, refuses a missing fingerprint at
`400` and a stale one at `409`, then calls `SettingsService.update` for each
changed module. Each accepted write appends one `audit_events` row with the
dashboard actor and the dotted-path diff. A partial infrastructure failure is
reported by guild/module and does not stop the remaining writes. This is the
same schema and the same write path as the single-guild editor; there is no
parallel template writer.

The preview reuses `labelFor` from the schema form, so a path reads
"Automod · Links" rather than a second labelling scheme.

## What we tried and rejected

- **A template table and saved templates.** Not needed for the first slice. The
  three presets are code-defined, versioned with the module catalog and covered
  by tests; a custom saved template needs a storage decision and a template
  editor, so it stays a later P6 slice. There is no migration in this pass.
- **A JSON fleet API now.** The HTML surface is the proven path. The public
  `/api/v1` template endpoints, scoped tokens and `Idempotency-Key` remain the
  separate P6 API block; adding half an API here would duplicate the authorization
  story without the token model.
- **Authorizing the fleet page with one bot call per guild.** The page lists the
  same manageable guilds as `/dashboard`; bot membership is enforced when a
  preview or apply is attempted, through the one authorization path. This avoids
  a burst of Discord calls on every page load and keeps the existing behavior.
- **Applying a template without a preview fingerprint.** A direct POST with a
  selected guild list would be a bulk write behind one CSRF token. The
  fingerprint makes "preview then apply" a server-verified sequence and also
  invalidates the preview if a setting changes in between.
- **Fingerprinting only the target values.** An external change can leave the
  target identical while making the displayed before/after diff stale. The
  fingerprint includes the changes as well as the target; the test changes one
  setting between preview and apply and expects `409`.
- **A separate template audit action.** Each module write is the unit the bot
  already audits. A `settings.template` row would double-count and would need a
  second diff concept. The row's `source: "dashboard"` and the diff identify the
  change; the template id is not stored in the audit row yet.
- **A Next.js shell for the fleet table.** Still unnecessary: the page is a
  server-rendered table and form, and it reuses the proven session/CSRF/auth
  stack. The ADR carrier decision stands.

  claimed.
