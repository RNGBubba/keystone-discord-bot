# Pass 60 — P7 community panels: rank card, greetings and the signed ticket panel

**Date:** 2026-11-03
**Phase:** P7
**Carrier:** `modules/community/src/panels.ts` plus the existing `packages/ui`,
`packages/i18n` and the shared component router. No new package, table or
command.

## What changed

- **One rank card builder.** `/rank view` and the **Rank card** user menu both
  call `rankPanel`; the level, XP and rank are the same `LevelingService` rows,
  and the line and footer come from the catalog (`en`/`de`). The two inline
  embeds are gone, so there is no second formatting path to drift.
- **The ticket panel is V2 and its button is signed.** `ticketPanel` renders a
  container with the title (default from the catalog), the description and one
  action row. `/ticket panel` signs a `ticket:open` id carrying the guild id
  with a 30-day TTL. `createFormRouter` became `createComponentRouter` and now
  hosts the `ticket:open` route; the handler parses the community settings,
  calls the same `TicketService.open` and replies with the thread link.
- **The legacy ticket id is retired.** The `keystone:ticket:open` branch was
  deleted from `apps/bot/src/community-events.ts`. The router returns `false`
  for an unknown id and no other listener claims it, so an old panel produces
  neither a ticket nor a reply.
- **Welcome and goodbye render through the UI layer.** They were plain `content`
  messages, not embeds. `greetingPanel` wraps the same substituted text in a V2
  container for the channel send; the welcome DM stays plain content. The
  operator message is not translated: it belongs to the guild, so the catalog
  has no key for it.
- **`CommunityMessage` speaks V2.** The port gained an optional `v2` tree and
  the Discord adapter converts it with `toV2Components`, sets
  `MessageFlags.IsComponentsV2` and never sends content/embeds beside it.
- **Tests.** The community tests assert the rendered V2 trees and the stored
  rows; the bot router tests prove one ticket row from a signed press, and that
  the legacy id, an expired id, a copied guild payload and a permission-gated
  route all refuse before a write. `community-events.test.ts` proves the legacy
  id no longer replies.

## What we tried and rejected

- **Keeping the ticket id unsigned and only adding an expiry.** Rejected: a
  plain expiry can be extended by anyone who edits the id, and the module does
  not hold the signing key. The HMAC in the kernel is already the contract.
- **A separate ticket interaction listener.** Rejected: it would duplicate the
  signature, expiry, guild and permission checks the router owns. One router,
  one set of refusals.
- **Translating the welcome/goodbye text.** Rejected: the message is written by
  the operator (`/tools welcome value:"..."`), so translating it would replace
  the guild's words. Only bot-owned chrome moved into the catalog.
- **Keeping the rank card as an embed beside `/rank view`.** Rejected: two
  copies of the same projection and formatting is exactly how the numbers and
  footer drift. One builder, two entry points.
- **An image renderer for the rank card.** Still rejected. It would add a
  canvas/native dependency and a second visual truth for no product gain; the
  card is text and says so.
- **A separate `ticketPanel` locale argument inferred from the interaction.**
  The command and the router both resolve `setup.locale` with `guildLocale`;
  the renderer takes the string and never reads settings itself, so it stays
  testable and has one source.
- **Deleting the panel on close.** Not attempted: a panel is a message with no
  stored row. The signed expiry is what makes an old copy stale, and deleting a
  support channel is not this service's job.
- **Moving the remaining community buttons (roles, giveaways, suggestions,
  polls) in the same pass.** Rejected for scope: this pass is the three named
  surfaces. Those ids are named as still legacy in the journal and can follow.

## Verification

- `pnpm typecheck` — pass.
- `pnpm test` — **623 tests in 91 files**.
- `pnpm probe:live` — **25/25**, adding `web-community-panels` over Postgres:
  the German and English rank cards matched the stored `levels` row; welcome and
  goodbye kept their substitutions and rendered as V2 with no content; the
  German ticket panel posted a signed id and one press wrote exactly one open
  `tickets` row; the legacy `keystone:ticket:open` id produced no reply and no
  row; expired, cross-guild and permission-gated ids were refused. The probe
  constructs discord.js objects and passes them through `asComponentInteraction`;
  **a live gateway click or member join is not claimed.**
- `pnpm check` — green (typecheck, tests, budget, claims, intents, channels,
  memory).
- `pnpm build` — pass.

## Next

The remaining legacy community button ids (`keystone:role:`, `keystone:roles:`,
`keystone:giveaway:enter:`, `keystone:suggest:`, `keystone:poll:`) still use the
old unsigned format and their own listener. P7 also still owes the untranslated
command replies/descriptions outside the form and community panels, and a
human-client proof of a gateway click, right-click and modal submit.
