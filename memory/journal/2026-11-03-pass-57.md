# Pass 57 — P6 session idle timeout and Discord refresh-token path

**Date:** 2026-11-03
**Phase:** P6
**Carrier:** the existing framework-free `apps/web` session seam. `auth.ts`, the
session store, `oauth.ts` and migration 0020 are extended in place; there is no
second session table, no second token store and no new process.

## What changed

- **Idle is its own clock.** `web_sessions` gains `last_seen_at`, separate from
  `created_at` (rotation) and `expires_at` (the absolute 7-day lifetime).
  `AuthService.session` refuses a session whose last activity is older than
  `idleTimeoutMs`, deletes the row, and returns no session; activity is written
  at most once per `touchIntervalMs` (30s in the runtime) so a dashboard burst is
  one write. Activity never moves `expires_at`, and rotation sets `last_seen_at`
  in the same write that re-keys the cookie.
- **Idle is configurable with a safe floor.** `WEB_SESSION_IDLE_MS` defaults to
  30 minutes and rejects anything below one minute, so a typo cannot disable the
  check. The instance page prints the active window beside the absolute lifetime
  and rotation interval.
- **Refresh is reachable and sealed.** The OAuth port now returns
  `refreshToken`/`expiresInSeconds` from the code exchange and exposes
  `refreshToken(refreshToken)`. `AuthService.complete` seals the refresh token
  with the same `SecretBox` as the access token and records
  `accessExpiresAt` (Discord's `expires_in`, capped at the session's absolute
  expiry). When the access token expires, `resolve` refreshes before any route
  runs, seals the rotated token, and persists the new access token, rotated
  refresh token, expiry and activity in one `updateTokens` write. A session with
  no refresh credential and an expired access token is deleted rather than
  pretending to work.
- **One refresh per session.** `AuthService` keeps an in-process map of in-flight
  refreshes keyed by session id; two concurrent requests await the same promise
  and spend the rotating credential once. This matches the one-web-process
  deployment the repo already documents; a second replica would need a shared
  lock, which is named as a limitation rather than silently assumed.
- **Refusal is permanent, transport failure is not.** A 400/401 from Discord's
  token endpoint is `OAuthRefreshRejected` and deletes the session; any other
  failure leaves the row so a later request can retry instead of logging a user
  out on a network blip.
- **Logout revokes the grant, not just today's token.** With a refresh token
  stored, revoking only the access token would leave the grant able to mint a
  replacement. Logout now revokes the sealed refresh token with
  `token_type_hint=refresh_token`; a session created before refresh storage
  falls back to the access token. The best-effort rule is unchanged: the local
  row is deleted even when Discord is unavailable.
- **Migration 0020.** Adds `refresh_token`, `access_expires_at` and
  `last_seen_at`. Existing rows get `access_expires_at = expires_at` (no refresh
  credential, so they last until their absolute expiry) and one idle window from
  deploy, because their last real activity is unknowable.
- Tests: three HTTP tests (stale session refused and deleted with the timestamp
  moving inside the window; one refresh for two concurrent requests with a
  rotated sealed token; a spent refresh token refused with the session deleted)
  and one PGlite test (activity and credential replacement in one write, missing
  row returns false). The existing logout tests now assert the refresh grant is
  revoked.

## What we tried and rejected

- **A second session or token store.** Rejected: the existing `SessionStore`
  already has the row, the hash and the sealing boundary. Adding `touch` and
  `updateTokens` is smaller and keeps one credential lifecycle.
- **Sliding the absolute expiry on every request.** Rejected: that turns a 7-day
  maximum into a forever session for an active browser. Idle and absolute
  lifetimes stay separate, and activity only moves `last_seen_at`.
- **A per-request `last_seen_at` write.** Rejected: a dashboard page can load
  many resources; a 30-second touch interval keeps the idle guarantee without a
  write per asset.
- **Storing the refresh token in plaintext or in the browser.** Rejected: it is
  the durable half of the Discord grant. It is sealed at rest and never leaves
  the server, exactly like the access token.
- **Refreshing without rotation.** Rejected: Discord rotates on every refresh;
  keeping the old value would make a later retry present a spent credential.
  The adapter stores the new sealed value in the same write, and a test replays
  the old one to prove the refusal branch deletes the session.
- **A Redis or Postgres advisory lock for refresh.** Rejected for this slice:
  the web carrier is one process, so an in-process promise is the honest
  guarantee. The limitation is written in the vault; a multi-replica deployment
  must make it shared before claiming it.
- **Deleting the session on every refresh failure.** Rejected: a network blip
  would sign everyone out. Only a permanent refusal deletes; a transport failure
  returns 401 for that request and leaves the row for a retry.
- **Revoking only the access token on logout.** Rejected once the refresh token
  is stored: the grant would survive logout. The probe now asserts the revoked
  hint is `refresh_token`.
- **Measuring the probe's idle/expiry against Postgres `now()`.** The probe
  freezes `authClock`, while Docker's clock drifted seconds ahead, so an
  "expired" row was still in the future to the service and the refresh never
  ran. Rejected: the probe writes timestamps against `authClock`, the same clock
  the service reads. This is why the live check now passes for the right reason.

## Verification

- `pnpm typecheck` — pass.
- `pnpm test` — **573 tests in 85 files**.
- `pnpm probe:live` — **23/23**, adding `web-session-idle-refresh` over real
  local HTTP on Postgres: a session 4 minutes into a 5-minute window was
  accepted and its `last_seen_at` moved; 6 minutes idle returned `401` and the
  row was gone; an expired access token was refreshed exactly once for two
  concurrent requests; the rotated sealed refresh token and new access expiry
  were stored; restoring the spent refresh token made the next request `401` and
  deleted the session. The existing `web-session-hardening` check now asserts
  logout revoked the refresh grant. The probe's OAuth exchange, refresh and
  revocation are fake, so **live Discord login, refresh and revocation are not
  claimed**.
- `pnpm check` — **green**, including `memory:check` at 3552/3552 checks.
- `pnpm build` — **green** (bot, worker and web bundles).
