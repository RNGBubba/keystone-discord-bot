# Pass 64 — P7: moderation's last unsigned buttons join the router

**Date:** 2026-11-03
**Phase:** P7
**Carrier:** `packages/kernel/src/components.ts`, `modules/moderation/src/cases.ts`,
`apps/bot/src/moderation-buttons.ts`, `apps/bot/src/components.ts`,
`apps/bot/src/runtime.ts`, `scripts/live-probe.ts`. No new package, command, table
or feature.

Appeal and verify were the last component ids in the tree that bypassed the
signed, expiring router. They existed because a DM interaction has no guild: the
verify button had to name both the guild and the member, and two 19-digit
snowflakes do not fit the signer's 40-character payload budget. Pass 61 named
that as the one explicit exception. This pass removes it.

## What changed

- **The router can read a guild from a signed payload.** A route may now declare
  `guildFromPayload(payload)`. The router resolves the id's guild as
  `interaction.guildId ?? route.guildFromPayload(payload)`, uses it for the
  `guildOnly` gate, refuses a click where the interaction guild and the payload
  guild disagree (`component.wrongGuild`, added to English and German), and
  passes the resolved guild to the handler as `ComponentRouteContext.guildId`.
  Signature and expiry checks are unchanged and still run first. A handler no
  longer has to trust `interaction.guildId` for a DM id.
- **The verify payload is `<guild>_<user>`.** `verifyCustomId` signs that pair;
  two snowflakes plus the separator are 39 characters, inside the existing
  budget. `_` is safe because the id format splits on `:`; the payload regex
  already accepted `_`. `parseVerifyPayload` returns `undefined` unless the
  payload is exactly two non-empty parts. The DM path is therefore bound to the
  guild in the signature, not to a gateway cache or a stored hint.
- **The appeal id signs the case id, and the handler checks the guild.** The
  payload has no room for a guild, so `handleAppealButton` reads the case and
  refuses when `record.guildId` is not the interaction's guild. The target-only
  rule and the operator's `appealsEnabled` switch are unchanged.
- **Both handlers are routes.** `registerModerationRoutes` registers
  `appeal/open` and `verify/complete`; `createComponentRouter` calls it, so the
  composition root's single router table owns every id. The old
  `parseModerationButtonId`, `handleModerationButton`, `keystone:` prefixes and
  the `isModerationButton` listener branch are deleted. An old-format id does
  not start with `k1:`, so the router returns false: no reply, no write.
- **`createRuntime` takes its gateway ports as one object.** Adding an eighth
  positional argument for the signer would have made the call site unreadable;
  the four action ports and the signer are now `RuntimePorts`. The security
  coordinator receives the signer too, so its notification's appeal/verify
  buttons are signed at the same instant as the case.
- **The safety net moved with the code.** `SecurityCoordinatorOptions.signer` is
  required, so a composition that tries to send a case panel without a signer
  fails at construction instead of shipping an unsigned button.

## The payload decision, and what was rejected

- **Widen the 40-character payload budget.** Rejected. Discord allows 100
  characters and the current longest legal id uses the budget tightly; raising
  it for every route to serve one pair would erode the headroom the signer test
  asserts, and the pair already fits at 39.
- **Mint a short-lived opaque handle and resolve it server-side.** Rejected for
  this slice: it needs a table, a write on every `/verify start`, a read on every
  click and a sweeper, and it moves the guild binding out of the signature into
  mutable storage. The deterministic pair keeps the id self-describing and
  stateless.
- **Put the guild in the namespace** (`verify:<guild>`). Rejected: the namespace
  grammar is 12 lowercase characters, and a guild id there would make routing
  match on data.
- **Let the handler read the guild from the case/member row only.** Rejected for
  verify: a copied id could then act on whichever guild the row named while the
  click happened elsewhere. The router-level binding refuses the mismatch before
  any store read. Appeal keeps the row check because its payload has no guild to
  bind.

## Component-id inventory (the grep)

```text
grep -rn "keystone:" --include=*.ts apps modules packages scripts \
  | grep -v "\.test\.ts" | grep -v "k1:"
```

The only production hits are a comment in `community-events.ts`, the unrelated
`keystone:cd:` cache prefix, and the probe's own legacy-id assertions. A second
grep for `customId` in `modules`, `apps/bot/src` and `packages/ui` shows every
panel id is built by `signer.sign(...)`; the remaining literal `customId`s are
modal text-input ids (form field keys) that arrive as fields of a signed modal
submit. No component id anywhere bypasses the router.

## What we tried and rejected

- **Keeping the legacy parser as a fallback.** It would leave two paths and let a
  pre-pass-64 panel keep working without a signature. Deleted, as pass 61 did for
  community.
- **An optional signer in `createRuntime`.** Two compositions (with and without
  panels) would be permanently supported and only one is real. The port object
  makes the dependency explicit; the security coordinator requires it.
- **Bundling guild + member into one base-36 or base-64 number.** It would fit in
  fewer characters but needs a custom codec and error cases for a saving we do
  not need at 39 characters.
