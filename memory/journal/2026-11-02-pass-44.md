## What changed

Bring-up and proof, not a feature pass. The product surface is unchanged.

**The live window is open**

- `docker compose up -d --wait postgres redis` started Postgres **16.15** and
  Redis 7 from the repository's own `compose.yaml`; both health checks pass.
- `pnpm db:migrate` — the project's explicit migration runner — applied all

- `.env` already pointed at localhost; no secret is recorded here.

**A real defect, found only live**

The first migration attempt failed:

```text
Error: UNSAFE_TRANSACTION: Only use sql.begin, sql.reserved or max: 1
```

`migrate()` sent `BEGIN` / `COMMIT` / `ROLLBACK` through `SqlRunner.exec`.
postgres.js pools connections and deliberately refuses raw transaction control:
the next statement can land on a different connection. PGlite accepted the same
calls, so 436 tests never saw it. That is exactly the class of defect the pass
existed to expose.

The fix is a driver transaction primitive, not a workaround:

- `SqlRunner` now requires `transaction(work)`.
- The Postgres runner uses `client.begin`, which reserves one connection for the
  callback, and passes a transaction-scoped runner to the work.
- The PGlite runner keeps its `BEGIN` / `COMMIT` / `ROLLBACK` sequence behind the
  same interface.
- `migrate()` calls `runner.transaction`; the error message still names the
  migration that failed and that it was rolled back.
- `packages/db/src/migrator.test.ts` adds two PGlite regressions: a failed
  multi-statement migration leaves neither its table nor its ledger row, and a
  successful migration commits both.

**`pnpm probe:live`**

A new operator command, deliberately **not** part of `pnpm check` (the gate must
pass with no database or network). It exercises and records:

| Check | Evidence |
| --- | --- |
| `postgres-migrations` | 13 applied, 0 pending on Postgres 16.15 |
| `postgres-settings-restart` | write one settings row, close the pool, reopen, read the same value |
| `redis-shared-cooldown` | two cooldown clients: first allowed, second refused with ~2 s left |
| `bullmq-job-idempotency` | two enqueues with one key → one handler call and a completed Postgres receipt |
| `portability-dry-run` | `1 added / 0 changed / 0 removed`, no write |
| `portability-import-verify` | real bundle imported; post-import checksum verified |
| `portability-rollback` | applied import restored its pre-import backup; destination settings 0 |
| `portability-deletion-receipt` | receipt kept one setting and the guild row is gone |
| `web-health-postgres` | `/healthz` 200 with `database: postgres` on an ephemeral port |

The run writes `memory/machine/live.json`. `pnpm memory:render` turns it into
[[06-Operations/Live-Window|Live window]], so the human page and the machine
evidence cannot disagree. The page is generated; the probe is the only writer.

**Feature flags made honest**

Five rows moved from `liveVerified: false` to `true`, each naming the passing

- `portability.restore-and-config-hash`

**Environment claims**

README, `AGENTS.md`, `Status.md` and `Home.md` now state the live facts:

or when it omits either service.

## What we tried and rejected

- **Set `max: 1` on the Postgres client so raw `BEGIN` stayed on one
  connection.** Rejected. It would serialize every query in the bot to make a
  migrator detail work, trading production throughput for a workaround.
- **Reserve one connection by hand around the migration.** Rejected. It
  reimplements `client.begin`, including its release-on-throw behaviour, and
  leaves a second transaction concept in the codebase.
- **Run the migration SQL by hand with `psql` and call the window open.**
  Rejected. The operator command would still fail; the probe would be a demo of
  a path the product does not use.
- **Put `probe:live` inside `pnpm check`.** Rejected. The repository's rule is
  that the gate passes with no database, no network and no token. The probe is
  the explicit exception an operator runs.
- **Flip every `liveVerified: false` portability row.** Rejected. File imports
  (MEE6, generic CSV, ProBot/HTML transcripts) were not exercised, and the
  in-Discord import/delete path still needs a human client.
- **Reuse one idempotency key across probe runs.** Rejected after it failed:
  BullMQ keeps completed jobs by id, so the second run waited on the first run's
  job while its Postgres receipt had been cleaned. Each probe now uses a
  per-run key.

## Still not live

- A human slash `InteractionCreate`, right-click menus and the in-Discord
  `/export import` / `/export delete` path.
- Discord OAuth and a real authenticated dashboard session. `/healthz` proves
  the web runtime against Postgres, not a Discord login.
- A production `pnpm worker:start` process kept running. The probe instantiates
  the real `createBullWorker` with real Redis and Postgres receipts, but does not
  leave a worker daemon behind.
- Bot gateway events: a real member join, a human author through the content
  filters, live role grants, music playback. These remain memory-mode or
  adapter-only evidence.
- Analytics queries against live rows: the SQL store is migrated but no
  analytics read has run against Postgres.
