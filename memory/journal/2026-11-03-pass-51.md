# Pass 51 — P6 config export, import and drift

## What changed

**Export is a portable settings document, not a full backup.**
`apps/web/src/config-bundle.ts` builds `keystone.config` version 1: source guild,
export time, one `{ id, version, settings }` entry per registered module, and a
SHA-256 checksum over canonical JSON. Settings are the `SettingsService`
effective values, so importing into an empty guild reproduces what the source
actually runs. Credential-shaped keys are stripped before hashing. The download
route is `GET /dashboard/guilds/:id/config/export` and returns
`Content-Disposition: attachment` with a guild-named `.json` file.

**Import validates before it compares anything.** The same file is parsed and
verified in a fixed order: object shape, kind/version, every registered module
present exactly once, no unknown modules, checksum over canonical content, then
each module's own Zod schema. A structural or checksum failure is reported alone;
a schema failure names the module-qualified field path. The browser upload path
supports a real multipart file field and the URL-encoded hidden copy used by the
apply step. `parseConfigUpload` reads the CSRF token from the same body, so the
existing session -> guild authorization -> CSRF sequence still runs before any
setting is read.

**Preview and apply reuse the template plan.** `settings-plan.ts` now owns the
plan types and one canonical fingerprint, and both templates and config imports
call it. The import preview compares the parsed bundle with live settings using
`diffSettings`, renders the same before/after table, and writes nothing. Apply
recomputed the plan, refuses issues at `400`, refuses a stale or missing
fingerprint at `409`, then calls `SettingsService.update` per changed module.
Each accepted write appends one `audit_events` row with actor `dashboard`.
There is no second settings writer and no second validator.

**A baseline makes drift meaningful.** Migration 0015 adds
`config_baselines`: one row per guild, holding the applied bundle, its checksum,
source (`import`), and timestamps. The `ConfigBaselineStore` port has a
token-free in-memory adapter and a Drizzle adapter. Applying a bundle stores it
as the baseline even when the diff is empty; applying a stale preview stores
nothing. `GET /dashboard/guilds/:id/config/drift` compares baseline -> live for
every module and lists exactly the changed leaves. A guild with no baseline says
so; a stored row that no longer parses reports its checksum and an error instead
of pretending every setting diverged. A full portability restore or deletion
also clears the guild's baseline, because the settings it described are gone.

The carrier remains the framework-free `apps/web` HTML app. No Next.js shell,
React, template table, second settings schema or parallel audit ledger was
added.

## What we tried and rejected

- **Reusing the importer's full guild bundle.** It carries cases, members,
  levels, transcripts and audit rows. A config import must not create or delete
  moderation history, so the settings-only document is a different contract with
  its own kind/version/checksum. The canonical JSON helper is shared; the
  payload is not.
- **Writing the previewed plan to the session or a table.** The preview page
  carries the exact file in a hidden field and the fingerprint binds the apply.
  Server-side preview state would need expiry, cleanup and a second store; the
  checksum already proves the re-uploaded file is the one displayed.
- **Applying a bundle without a preview fingerprint.** That is a bulk settings
  write behind one CSRF token. The fingerprint makes preview -> apply a verified
  sequence and catches settings changed in between.
- **Treating a missing baseline as empty settings.** That would show every
  default as drift on a fresh guild. No baseline is a state the page names, not
  a zero to compare.
- **Updating the baseline on every settings write.** Drift would then always be
  zero, and the feature could never answer "what did the operator intend?". Only
  an explicit import stores a baseline; an out-of-band edit is precisely what
  drift should show.
- **A generic JSON API for import/export now.** The HTML flow is the proven
  surface. Scoped tokens, `Idempotency-Key`, OpenAPI and webhooks remain the
  separate P6 API block; a half-API would duplicate authorization without the
  token model.
- **A Next.js shell for the upload form.** The multipart parser is twenty lines
  of Node code and the page reuses the existing session, CSRF and authorization
  stack. The ADR-0016 carrier decision still holds.

## Verification

- `pnpm typecheck` green.
- Focused tests: `config-bundle.test.ts` (7), `config-baseline-store.test.ts`
  (1), `web.test.ts` (25). The web tests cover export authorization, a real
  multipart preview, no writes during preview, a checksum-edited file at `400`,
  a wrong fingerprint at `409`, apply `302` with one audit row and a stored
  baseline, clean drift, one drift after an out-of-band update, a stale preview
  after a settings change, CSRF, cross-guild authorization, and a no-baseline
  page that does not invent drift.
- Full `pnpm check` green after the memory update: typecheck, **515 tests / 76
  files**, budget **20/100 roots · 141 subcommands · 161 actions · 4 menus**,
  claims, intents, channels and memory.
- `pnpm probe:live` **16/16** on Postgres 16.15 + Redis, after applying migration
  0015. The new `web-config-export-import-drift` check exports a 12-module
  checksummed file, uploads it to the second guild as multipart, previews the
  diff without writing, gets `400` for an edited checksum and `409` for a wrong
  fingerprint, applies the real plan (`302`, one audited AI write, baseline
  stored), sees "No drift", then changes one setting out of band and sees exactly
  one changed value. The OAuth exchange uses a fake port; no Discord login is
  claimed.
- `memory/machine/live.json` records `live-2026-11-03` and 16 checks.

## Next

P6 still needs custom saved templates and analytics aggregates, then session
refresh/revocation, per-route rate limits, `owners[]`, and the public API
token/scopes/webhooks/OpenAPI block. The live Discord OAuth round trip is still
the missing dashboard proof. No P7, P8 or P10 work was started.
