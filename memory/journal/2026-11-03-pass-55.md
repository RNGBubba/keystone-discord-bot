# Pass 55 — P6 scoped API tokens, per-token limits and a generated OpenAPI document

**Date:** 2026-11-03
**Phase:** P6
**Carrier:** the framework-free `apps/web` app, unchanged. This slice adds a
principal to the existing `/api/v1` handlers, not a second API service.

## What changed

- **One token port.** `packages/kernel/src/api-tokens.ts` declares
  `ApiTokenStore` (create, find by hash, get, list, revoke, touch) plus the three
  scopes, `isApiScope`, `tokenIsActive` and an in-memory adapter. Migration 0018
  creates `api_tokens`; `DrizzleApiTokenStore` is the Postgres adapter and
  `createApiTokenStore` the factory. A row is bound to one guild, stores the
  SHA-256 hash of the `keystone_…` secret and the scopes as JSONB.
- **The secret is shown once.** `ApiTokenService.issue` mints the secret, hashes
  it, stores the record and returns `{ record, secret }`. Only the token page's
  creation response renders the secret; `list` and every later page never do.
  Issue and revoke pass the same guild write gate as a settings change
  (session → guild authorization → CSRF) and append one `api_token.issue` or
  `api_token.revoke` audit row with `source: "dashboard"`.
- **Bearer authentication feeds the same handlers.** `request-context` resolves
  `Authorization: Bearer` into `ctx.bearerPresent` / `ctx.apiToken` once.
  `authorizeApiGuild` is the one guild check: a token must stay inside its guild,
  carry the route's scope and still find the bot in that guild; a session falls
  through to the existing `authorizeGuild`. `/api/v1/me` and `/api/v1/guilds`
  already answer a token with its own identity and guild. `PATCH settings` keeps
  one write path: a token is the actor (`token:<id>`, source `api`) and needs no
  CSRF because it has no cookie to forge; a session still does.
- **Per-token windows.** `rate-limit.ts` gains an `apiToken` class (60/min). The
  server buckets a bearer request by `token:<id>`, or by address when the secret
  is unknown so guessing cannot mint a budget. The session-backed `api` class is
  unchanged.
- **A document that answers to the routes.** `apps/web/src/openapi.ts` is an
  operation table (method, path, auth, scopes, parameters, body) rendered into an
  OpenAPI 3.1 document served at `GET /api/v1/openapi.json`. `openapi.test.ts`
  walks `ROUTES` and `API_OPERATIONS` in both directions with sample paths, so a
  new `/api/v1` route without an entry, or an entry whose route is gone, fails.
  Both principals are declared in `components.securitySchemes`; scopes are listed
  as `x-keystone-scopes` from the same `API_SCOPES` constant the routes check.
- **UI.** `GET /dashboard/guilds/:id/tokens` lists the guild's tokens with scope,
  status, last use and expiry; the form issues one; the newest creation response
  shows the secret in a `<pre>` with a copy-once warning. A revoke button posts
  through the guild write gate.
- Tests: 5 service tests (hash-only storage, one-time secret, input rejection,
  expiry, idempotent revoke), 3 OpenAPI drift/security tests, 4 HTTP tests
  (issue → use → scope/guild refusals → revoke → audited issue/revoke; token
  `PATCH` without CSRF; per-token `429` and recovery with a second token
  unaffected; invalid issuance stores nothing) and 1 PGlite test for the store
  (hash round trip, guild scoping, one revocation, retained row, last use).

## What we tried and rejected

- **A second `/api/v1` handler for tokens.** Rejected: the plan's whole point is
  that the token authorizes the existing read and write path. Every route now
  calls `authorizeApiGuild`, which returns the same `DiscordGuild` a session gets.
- **A hand-maintained `openapi.yaml`.** Rejected: it would drift the first time a
  route changed. The document is generated from the table, and the table is
  checked against the route registry in the test suite.
- **Storing the secret encrypted instead of hashed.** Rejected: nothing needs to
  display a token after creation. A one-way hash makes a database read useless to
  an attacker, the same rule the session table follows.
- **Guild-less tokens or a user-level token.** Rejected for this slice: a token
  is a guild-scoped automation credential, and the scope check is a ceiling on
  top of the bot-membership check, never a replacement for it.
- **A separate token rate-limit store or Redis counter.** Rejected for the same
  reason as pass 54: the web process is one container. A shared counter is a
  multi-process deployment concern, not something to add silently.
- **Letting a bearer token skip the bot-membership check.** Rejected: a token
  whose guild has removed the bot must stop reading immediately.
- **`Idempotency-Key` and webhooks in the same pass.** Deliberately deferred:
  they are a second half of the API block (delivery, signing, replay storage) and
  would double this slice without proving the token core.

## Verification

- `pnpm typecheck` — pass.
- `pnpm test` — **553 tests in 82 files**.
- `pnpm probe:live` — **20/20**, adding `web-api-tokens` over real local HTTP on
  Postgres: an owner issued a `guild:read` token from the dashboard, the secret
  was shown once and only its SHA-256 hash reached `api_tokens` (the plaintext
  count query returns zero); the token used the existing overview and guild-list
  handlers and `/api/v1/me` returned its own identity; a foreign-guild call and a
  wrong-scope analytics call were `403`, anonymous and bogus bearers `401`; the
  first use stamped `last_used_at`; a tight per-token window returned `429` with
  `Retry-After` and recovered in the next window; revoke returned `302` and the
  token then failed with `401`, a second revoke wrote no audit row, and exactly
  one `api_token.issue` and one `api_token.revoke` dashboard row named the owner;
  `/api/v1/openapi.json` named both principals and the analytics scope. The
  probe's OAuth exchange is fake, so live Discord login is **not claimed**.
- `pnpm check`, `pnpm build` — run in the gate.
