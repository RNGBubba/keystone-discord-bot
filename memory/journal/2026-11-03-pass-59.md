# Pass 59 — P7 i18n, per-guild locale and derived command localizations

**Date:** 2026-11-03
**Phase:** P7
**Carrier:** a new framework-free `packages/i18n` plus the setup module's settings
schema, `apps/bot/src/components.ts` and `apps/bot/src/adapt.ts`. No dependency
was added; the catalog is plain TypeScript.

## What changed

- **`packages/i18n` exists.** `en` is the type source: every message is a
  function whose arguments are declared once, and `Catalog` maps each key to the
  same argument list. A translation therefore cannot drop an interpolation,
  rename an argument or give a plural argument a different type without a
  compile error. `t(locale, key, ...args)` resolves through one fallback chain —
  requested locale, English, then `FALLBACK_MESSAGE` — so a raw key can never
  reach a user. `resolveLocale` and `localeFromSettings` treat an unknown stored
  value as `en` rather than throwing in a render path.
- **The shipped copy is `en` and hand-written `de`.** The translated surfaces
  are the form panel, the Apply modal's receipt, the missing-field refusal, the
  review queue, the component router's expired/permission/guild refusals, and
  the ping/about/form command and option descriptions. Nothing else was added to
  the catalog: an unreachable key is a promise the bot does not keep.
- **The per-guild locale is `setup.locale`.** Setup already owns guild-wide
  operator settings, so its schema declares `locale` as a `z.enum` over the
  supported list. `/config set setup.locale`, the dashboard schema widget and
  the API all validate the same values through `SettingsService`; an
  unsupported value is refused and the stored locale is unchanged. There is no
  second settings mechanism and no new table.
- **Discord command localization is derived, not maintained.** `buildCommandJson`
  asks the catalog for `command.<root>.description`,
  `command.<root>.<sub>.description` and
  `command.<root>.option.<name>.description` and emits
  `description_localizations` for every non-default locale that has the key. A
  command with no translation carries no map and stays English; the name is an
  invocation identifier and is deliberately not translated.
- **Panels and components read the guild's locale.** `/form panel` reads
  `guildLocale(ctx.config, guildId)` before rendering, and the component
  listener resolves the locale once per interaction and passes it to the router,
  which passes it to each handler. The router's three shared refusals come from
  the same catalog.
- **Tests.** A new `packages/i18n` suite (fallback, unknown locale, missing key,
  command lookup), setup schema tests, a dashboard widget test proving the
  `select` comes from the same enum, adapter tests for the derived localization
  map and the English-only case, and bot route tests for a German guild.
- **Live probe.** `web-component-panels` now sets `setup.locale=de` through the
  real `SettingsService`, asserts the stored value, rejects `locale: "xx"` at the
  schema, renders the panel/receipts/refusals/review list in German, checks a
  partial catalog falls back to English and an unknown key returns a sentence,
  reads the German command description from the adapter, then resets the record
  and re-checks the same panel and refusal in English.

## What we tried and rejected

- **i18next.** Rejected: it is a runtime dependency, its interpolation strings
  are unchecked, and a typo in a placeholder ships silently. The typed catalog
  gets the same result with the compiler as the reviewer and no new package.
- **Storing the locale in the existing `guilds.locale` column.** Rejected: that
  column is a portability snapshot detail and writing it would create a second
  settings path beside `SettingsService`. `setup.locale` reuses the validated
  write path the bot, dashboard and API already share; the column stays what it
  was.
- **A CLDR plural-rules library.** Rejected for two hand-written locales: the
  English source declares `count: number`, and each catalog decides its own
  plural ending inside the function. A third locale with complex plural rules
  would justify the library; two do not.
- **Translating every module's command output now.** Rejected: that is hundreds
  of strings across twelve modules and would either ship a catalog of unreachable
  keys or machine-translated prose nobody reviewed. The pass translates the
  surface that was just built and names the rest as open.
- **`name_localizations` for command names.** Rejected: a localized invocation
  name would make the same command two identifiers in two clients, and the
  catalog keys are already keyed by the stable English name.
- **A per-command localization table in `scripts/`.** Rejected: it would drift
  from the strings the bot renders. The descriptions are derived from the same
  catalog at build time.
- **Returning the key when a translation is missing.** Rejected: `form.review.
  pending` tells a user nothing and looks like a bug. The fallback is English and
  then a plain sentence, and the probe asserts the sentence.
- **A user-facing locale command.** Deferred: the locale is operator state like
  every other setting, so `/config` and the dashboard already own it. A dedicated
  command would cost a subcommand and duplicate the schema.
